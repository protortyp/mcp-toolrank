## Source feasibility

A pinned 149 MB shard from Toucan's Kimi-K2 configuration has 12,963 rows. The probe matched all named targets to available tool definitions and source metadata in 8,404 rows. Of those, 3,781 had a GitHub repository and a candidate permissive license declaration for every target after screening direct MCP-Atlas server names. This covered 109 repositories and 648 distinct target tools. All 15 most represented repositories had a currently observable MIT license file on GitHub. This is a feasibility count. Match collected definitions to versioned source files, preserve required notices, validate the query and target pairing, and resolve forks and aliases before using rows. The sampled shard contains multiple targets per matched request. The canonical source key should identify the original repository and provider family across repo forks, wrapper servers and aliases. Keep a source manifest with the dataset revision, shard and row ID, file and commit, license evidence, and notices. Extract the original request and applicable static tool specification. Exclude arguments, service responses, discovered account data, and executed traces. Sample-check whether each target contributes to the user request. Treat non-target tools as unknown until a negative sampling rule can rule out equivalent or complementary tools.

ToolACE and xLAM declare Apache-2.0 and CC BY 4.0 respectively. Both are represented as source families in ToolRet. Keep them outside this proposal to simplify contamination control. 2. Aim for 5,000 to 20,000 verified training requests as a first local run, capped per provider. Use multi-positive contrastive training so two required tools are never negatives for one another. Use the development split for training choices and abstention calibration.

Reuse the pilot's hardware protocol and add latency for selector ranking on a precomputed realistic catalog. Use ToolRet for secondary reporting only.
